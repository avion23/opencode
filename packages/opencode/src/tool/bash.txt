Execute bash commands in a persistent shell with optional timeout. Use the `workdir` parameter for directory changes; never use `cd <dir> && <command>`.

For terminal operations (git, npm, docker) only. Use specialized tools (Glob, Grep, Read, Edit, Write) for file operations, not Bash.

Before creating directories/files, verify the parent exists. Always quote paths containing spaces.

Provide 5-10 word descriptions for each command. Run independent commands in parallel; chain dependent commands with '&&'. Use ';' only when you don't care if earlier commands fail.

Output is truncated automatically; don't use head/tail to limit it.

# STRATEGIC USE

1.  **VERIFICATION**: This is your primary tool for `testing`, `linting`, and `building`. Use it to prove your code changes are correct.
2.  **ENVIRONMENT**: Use for `git` operations, package management (`npm`, `pip`, `go mod`), and running project-specific scripts.
3.  **UTILITY**: Use for file system navigation (`ls`), but prefer specialized tools (`Read`, `Glob`) for content operations.

# PROTOCOL

*   Do not ask for permission to run standard commands (`git status`, `npm install`, `pytest`).
*   Chain dependent commands with `\u0026\u0026`.
*   Run independent verification steps in parallel.
*   CRITICAL: Do not use `echo` to communicate with the user.

# Safety Protocol

- NEVER update git config or run destructive commands (push --force, hard reset) unless explicitly requested
- NEVER skip hooks (--no-verify, --no-gpg-sign) unless explicitly requested
- NEVER force push to main/master
- Avoid git commit --amend. Only amend when ALL conditions met: (1) explicitly requested or pre-commit hook modified files, (2) HEAD was created by you in this conversation, (3) not pushed to remote
- NEVER commit unless explicitly asked
- Never use git commands with -i flag (interactive) since they're not supported
- Do not create empty commits

# Commit workflow

1. Run git status, git diff, git log in parallel to understand state
2. Analyze changes and draft commit message focusing on "why" not "what"
3. Do not commit files containing secrets (.env, credentials.json)
4. Stage, commit, then verify with git status

# Pull requests

Use gh command for GitHub tasks. When creating PRs:
1. Run git status, git diff, check remote tracking, git log in parallel
2. Analyze ALL commits (not just latest) and draft PR summary
3. Create branch if needed, push with -u, create PR using gh pr create
4. Return PR URL

Do NOT use TodoWrite or Task tools for git operations.
